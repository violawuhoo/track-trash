### 1.3 真正的瓶颈不是数量，是语义拥挤度

数量上 145 >> 26，**但同一形状被多个 kind 共用**，所以「复用既有形状」天然有语义撞车风险。
下表是**每个 kind 的独占形状池**——只有这些形状复用时不会跟别的 kind 撞语义。

| kind | 用到的形状数 | **独占形状** | 独占形状的剩余色位 |
|---|---|---|---|
| `base` 区域杂物 | 22 | **11**：wrench, book, card, sun, bolt, cloth, ticket, arrow, drop, rock, star | 37 |
| `mid` 中间产物 | 8 | **6**：wire, bracket, signal, bed, tent, bowl | 23 |
| `ship` 部件 | 8 | **2**：clock, bar | 8 |
| `commission` 委托 | 7 | **3**：shop, person, hands | 11 |
| `accident` 意外 | 10 | **5**：map, page, question, blob2, dice | 19 |
| `keepsake` 纪念品 | 5 | **4**：badge, brick, broken, candle | 15 |

**形状层瓶颈清单（必须绕开）**

- `engine`：**5 色占满，剩余 0**。它同时被 base / ship / commission 用，任何新物品都不得复用。
- `ring`：只剩 **purple** 一个色位，且已被 base+accident 共用。
- 只剩 2 色（`sheet` `rod` `flask` `sun` `rock` `blob` `wave`）：复用价值极低。
- 被 2–3 个 kind 共用的形状（`stack` `cell` `shield` `door` `cloud` `blob` `scribble` `sign` `page` `map` `badge` `ticket` `blob2`）：复用即语义串味。

**结论**：v3 需要 **17 个新形状**，理由有三——
① 语义分组要求新物品「不看名字就能归类」，而既有 45 形状里能表达"新功能语义"的已经被 base/mid 占满；
② `engine`/`ring` 等高价值形状已被多 kind 抢占，剩余槽位不足以承载 4 个新分组；
③ **17 个新形状 × 5 色 = 85 个全新槽位**，让"每件新物品独占一个新形状 + 一个颜色"成为可能 —— 这是断言 D 天然通过的最短路径。

## ② 新增形状词表（17 个）

### 2.1 命名规则

- `ShapeName`（几何名）用**单数英文小写名词**，与既有 `tape / wrench / bracket / shield / door / bowl / badge / brick / candle` 同风格，不加前缀后缀。
- `icon` 键**直接等于几何名**（`icon: 'coil'` → `SHAPE_OF.coil = 'coil'`），一一对应、不设别名。理由：既有别名（`doorway→door`、`medal→badge`、`note→scribble`、`aura→wave`、`speaker→engine`）是 v1 遗留的语义混淆源，v3 不再扩大。
- 全部路径画在 **48×48 坐标系**内（`SHAPE_VIEWBOX = 48`）。

### 2.2 区分判据（"44px 手机屏上一眼分辨"的可执行定义）

我把判据拆成四条，**四条全过才算合格**：

**判据 1 · 剪影不重叠（硬门槛，可量化）**
把每个 SVG 形状在 32×32 网格上光栅化，取 **填充掩膜 ∪ 描边掩膜**（"全墨掩膜"，即玩家在 44px 屏上真正看到的轮廓），两两算 IoU。

> 校准基线（既有 45 形状的 990 对组合，旋转感知）：
> **max 0.864**（`ring`↔`engine`）、**p90 0.531**、median 0.257、p10 0.095。
> 既有库里最像的一对（`ring`/`engine`）IoU 高达 0.864 却仍被认为可区分 —— 因为它们内部镂空结构完全不同。
> 但既然要求"一眼分辨"，我把门槛定得比既有库 p90 更严：

> **新形状 vs 任一既有形状的「全墨 IoU」必须 ≤ 0.52（严于既有库 p90 0.531）。**

**判据 2 · 内部负空间可辨**
不得依赖"内部细节"来区分两个形状（28 世界单位下细节会糊）。判据 1 之外，还要求新形状与最近的那对既有形状在**填充区**上有结构性差异（实心 vs 镂空 / 开口方向 / 长宽比 ≥ 1.4:1）。

**判据 3 · 颜色双编码**
任何两件新物品不得共用同一 `(形状, 颜色)`。即"形状定类别、颜色定个体"的双通道编码。

**判据 4 · 旋转克制**
形状内建旋转 **≤ 8°**。既有 `map` 用 `-10°`、`card` 用 `-8°`；再大就会和 `ItemCard` 的按 id 哈希微旋转（±2.7°）叠加成乱转，反而更难认。
**17 个新形状全部正置，无一内建旋转** —— 包括 `key`：它的"斜置感"由路径本身的斜杆（20,19→39,38）构成，不需要旋转。
靠负空间、长宽比、开口方向区分，不靠转。

### 2.3 词表（按功能分组排列）

> ⚠️ **实现前必读（对 17 个新形状全部适用）**：
> `shapeMarkup()` 的外层是 `<g fill="none" stroke="${PALETTE.ink}" ...>`。
> **开放 path（折线）上的 `fill` 是空操作** —— 不产生面积、颜色不生效，实际继承外层墨黑描边。
> **要指定颜色的线条一律用 `stroke="…"`**；**要挖空/挖洞必须用闭合路径**（如 `key` 的钥柄孔是闭合圆，`fill=paper` 才有效）。
> 详见 §2.5 的通用规则与三个正确写法示例。

### 2.5 可直接落码的 markup（全部 17 个形状）

> **这是实现者唯一需要照抄的东西。** 格式与既有 45 个形状完全一致：
> `(fill: string) => \`...\``，**内部不写 `stroke-width`**、**不带投影**、**不用渐变/模糊/CSS 变量**；
> 描边（`stroke` / `stroke-width` / `linecap` / `linejoin`）由 `shapeMarkup()` 的统一外层 `<g>` 提供。

> ⚠️ **通用规则 1 · 开放 path 上的 `fill` 是空操作**（对 17 个形状全部适用）。
> `shapeMarkup()` 的外层是 `<g fill="none" stroke="${PALETTE.ink}" ...>`，
> 所以 `M20 22h14` 这种**开放折线**写了 `fill="…"` 也不产生任何面积 —— 颜色完全不生效，
> 它实际渲染出来的是**继承外层的墨黑描边**。
> **要指定颜色的线条，一律用 `stroke="…"`；要挖空/挖洞必须用闭合路径**
> （`key` 的钥柄孔是闭合圆，`fill=paper` 才有效）。
> （既有先例：`broken` 的裂纹用 `stroke="${PALETTE.paper}"`；`page` 的透印线用 `stroke="${fill}"`；
> `brick` 的砖缝是裸 path，直接继承外层墨黑。）
>
> ⚠️ **通用规则 2 · 渲染方式只有三种**，下表逐段标注：
> | 标记 | 含义 | 用法 |
> |---|---|---|
> | **主填充** | 形状本体 | `fill="${fill}"`，**必须闭合**（`z` 结尾 / `circle` / `rect`） |
> | **墨色描边** | 线条、镂空边界、内部细节 | **裸 path**（不写 `fill`，继承外层墨黑） |
> | **纸白填充** | 挖洞/透印/落点 | `fill="${PALETTE.paper}"`，**必须闭合** |
>
> ⚠️ **通用规则 3 · 几何约束**（落码前已逐条机器校验）：
> 全部坐标在 **0–48** 内；图元最小尺寸 **≥3 格**；最细线段 **≥6 格**；
> **17 个形状全部正置，无一内建旋转**（避免与 `ItemCard` 的 ±2.7° 哈希微旋转叠加）。

> **IoU 结论**：17 个新形状 vs 45 个既有形状，**最大 0.483**（`placard` vs `bar`），门槛 0.52 ✅；
> 新形状两两最大 **0.369**（`pylon` vs `lamp`）✅。
> IoU 是「填充掩膜 ∪ 墨黑描边掩膜」双通道光栅下测得的 ——
> **开放 path 的 `fill` 不贡献面积，所以"填 paper / 删 fill / 改 stroke=paper"三种写法算出的 IoU 完全相同**，
> 可分辨判据的结论不受写法影响。

## ④ 取色规则（可执行，保证断言 D 天然通过）

### 4.1 一句话规则

> **先定形状，再定颜色；新物品一律取该形状的「空闲色位」——优先本组主色 → 本组副色 → 本组备用色 → 跨组借用色；一旦某色位被占用就顺延到下一个，绝不改形状去迁就颜色。**

### 4.2 五步法（照做即可，不需要人工试错）

**Step 1 · 选形状**
按 ③.3 的分配表：优先用本组的新形状（85 个全新槽位）；本组新形状用尽时，从**该 kind 的独占形状池**里取。

**Step 2 · 算该形状的空闲色位**
查 ① 的矩阵：该形状 5 色中标 `·` 的就是空闲位。**新形状的空闲位 = 全部 5 色。**

**Step 3 · 按本组色序取第一个空闲位**

| 组 | 取色顺序（从左到右） |
|---|---|
| 阶段 3 中间产物 | **orange** → yellow → mint → pink → purple |
| 第四支线委托物 | **mint** → pink → orange → yellow → purple |
| 前任日志载体 | **purple** → yellow → mint → pink → orange |
| 新纪念品 | **pink** → orange → yellow → mint → purple |

**Step 4 · 硬冲突才跨组借色**（本组色序全被占满时）
按**让位序**从先让的一方借色：

> **让位顺序：base → accident → ship → mid → commission → keepsake（越靠前越先让位）**
> 理由：`base` 33 件是背景噪音，改色的语义代价最低；`keepsake` 只有 6 件但每一件都是玩家的情感锚点，
> **最后让位，绝不因为新物品而改色**。

借色时借的是**该形状的空闲色位**，且**不得占用让位序中更靠后组的「主色 + 该组已有物品用过的色」**。
例：日志载体要 purple，但 `reel` 是新形状、5 色全空 —— 直接取 purple，不存在冲突。

**Step 5 · 收尾校验**
```
node scripts/check-assets.mjs
```
断言 D 期望输出 `组合数 N/N`，即每件物品的 `(形状, 颜色)` 唯一。
只要遵守 Step 2（只用空闲色位）与 Step 4（借色也只借空闲位），**D 必然通过**。

### 4.3 为什么这样能"天然通过"

- 断言 D 的失败条件只有一种：`两件物品的 (形状, 颜色) 完全相同`。
- 145 个空闲槽远多于 25 件新增物品，**只要每件新物品都落在空闲槽上，冲突在数学上不可能发生**。
- 真正的风险不是"槽位不够"，而是**语义串味**（新物品用了 base 的形状 + 同一个颜色，
  玩家在背包里把它认成旧物品）。Step 1 的"优先独占新形状" + Step 4 的"让位序"两条共同封住这个风险。

### 4.4 反面清单（明确不要做）

- ❌ 不要为了"好看"给两件新物品配同一个 `(形状, 颜色)`。
- ❌ 不要复用 `engine`（剩余 0 槽）；不要复用 `ring`（仅剩 purple，且已被 base+accident 共用）。
- ❌ 不要在 `keepsake` 组抢 `base`/`accident` 的主色，除非该形状确实空闲且对方组没用这个色位。
- ❌ 不要给新物品 `color` 赋 5 荧光色以外的值（`StickerColor` 类型 + 断言 A 的色值镜像双重约束）。

## ⑤ 前任日志载体的视觉表达 —— 结论

### 5.1 结论（一句话）

> **前任日志载体应当是「一个可辨认的物件轮廓」，而不是「一段被画成图形的文本卡片」。**
> 日志的**内容**走文本 UI（日记面板 / 物品详情里的长文本），日志的**载体**走 SVG 形状。

### 5.2 理由（四条）

1. **工程上：文本卡片在现有资产管线里没有落点。**
   `ItemIcon.tsx` 的 `SHAPES` 是**几何路径库**（`ShapeFn = (fill: string) => string`），不接受 `<text>`；
   `check-assets` 断言 B 要求每件物品的 `icon` 都能在 `SHAPE_OF` 查到形状。
   若把日志做成"带字的卡片"，就必须在 SVG 里画 `<text>` —— 而 Riso 视觉语言是**纯手绘墨黑描边 + 三色盘**，
   系统字体渲染的文字放进贴纸会立刻破坏风格一致性，且文字在 32 世界单位下不可读。

2. **可读性上：28 世界单位下靠细节分辨是不可行的。**
   `DESIGN-SYSTEM.md` 明确「28 单位下必须靠轮廓可辨，不能靠内部细节」。
   日志正文再短也不止 2–3 个字，塞进 32px 的贴纸里必然糊成一团。

3. **语义上：纸类形状已经被 base/accident 占用，复用会串味。**
   既有纸张家族 `sheet`(base/commission, 剩 2 槽) `page`(accident, 剩 4) `book`(base, 剩 4)
   `map`(accident, 剩 4) `card`(base, 剩 3) `ticket`(base, 剩 3) `scribble`(base/accident, 剩 3)
   —— 全部是高密度复用形状。日志载体若用 `page`，玩家会把它和既有的"一页废纸"（`wastepaper`, mint）
   归到同一视觉族，而这两个在叙事上完全不是一类东西。

4. **产品上：可读性属于交互层，不属于资产层。**
   前任日志是"要读的内容"，玩家会主动打开它。**载体图标的任务是让玩家认出"这是一件能读的记录"，
   不是让他在 44px 屏上读完它。** 把可读内容塞进贴纸等于把 44px 屏当成阅读器。

### 5.3 具体规格

| 层 | 形态 | 资产 |
|---|---|---|
| **载体本体（图形）** | 2 个新形状，`reel`（数据卷盘/磁带盘）+ `chip`（存储芯片） | 走 ② 的形状词表，48 格坐标。**已对账定色**：`reel` = purple（`log_reel1`）、`chip` = yellow（`log_chip1`）—— 与 §④ 的 accident 组色序「purple → yellow → mint → pink → orange」一致 |
| **载体变体（纸页类）** | 「前任写在纸上的记录」这一变体，**已对账**用 `page` / `map` / `question` / `blob2` 四个既有形状，**颜色取其空闲色位**（orange / purple / yellow / pink / mint），且**同形状不超过 2 件** | 复用既有形状，不新增 |
| **日志内容（文本）** | 不画成图形。由 UI 层承载：物品详情浮层的「日志」段落（日记面板 / 长文本折叠区） | 复用 `--fs-2xs`（12px）/ `--lh-tight`，行高 1.7；条目 ≤40 字/条（对齐 `DESIGN-SYSTEM` 描述 ≤40 字约束） |

| **容器** | 日志面板用 `--paper` 底 + 3px `--ink` 边 + `--shadow`（`4px 4px 0 ink`，**UI 层专用**，此处合规） | 复用既有 UI 组件 |

### 5.4 明确不做的三件事

- ❌ 不在 SVG 里画 `<text>` 或用路径模拟汉字笔画。
- ❌ 不为"日志"新增一个带字的形状（会同时破坏 Riso 风格与断言 B 的管线约束）。
- ❌ 不把日志正文写进 `items.ts` 的 `desc` 字段然后指望 desc 显示完整日志 ——
  `desc` ≤40 字是硬约束，它只够写一句"前任留下的记录本，最后一页写满了字"这种**钩子**，
  正文必须走独立的日志面板。

### 6.2 包体增量预估

**实测方法**：把 25 行真实感新物品（含真实中文 name/desc/tags、真实 kind/color/icon）与 17 个新形状的 markup
按**最终形态**插进源文件，对改前/改后分别 gzip（level 9），取差值。不是理论估算。

| 项 | 方法 | 实测增量 |
|---|---|---|
| 25 行物品数据 | `items.ts` 80 行 → 105 行，gzip 差 | **+677 B**（按 26 行实测 +704 B 折算，每行 ≈ 27.1 B） |
| 17 个形状路径 | `ItemIcon.tsx` 的 `SHAPES` 块插入，gzip 差 | **+763 B**（每形状 ≈ 44.9 B；对账后 `placard`/`plaque` 顶替 `pennant`/`flower`，图元数与体积同量级） |
| 17 个 `SHAPE_OF` 键 | 独立 gzip（保守上界，实际在文件内更省） | **+172 B** |
| **合计** | | **≈ 1,612 B ≈ 1.58 KB** |

**主包推算**

| | 数值 |
|---|---|
| 当前主包 | 158.88 KB（gzip） |
| v3 增量 | **+1.58 KB** |
| 之后 | **≈ 160.5 KB** |
| 红线 | 250 KB |
| **占红线比例** | **64.2%** |
| 剩余余量 | **89.5 KB** |

**结论：包体不是 v3 扩容的约束条件。**
按当前单价（每件物品 ≈27 B、每形状 ≈45 B gzip），剩余 89.5 KB 还能再吃 **约 3,000 件物品**或
**约 2,000 个形状**。即便把 v3 的上限从 25 件放大到 50 件、形状从 17 加到 25，增量也只有 ≈2.7 KB。

**附带说明（非包体，但同源）**

- **运行时纹理成本**：物品贴纸按 id 缓存（`sprites.ts`），地面同屏 ≤18 件贴纸。
  新增物品不增加同屏纹理数，只在背包里首次出现时多光栅化一次 —— 一次性成本，可忽略。
- **构建产物体积**：17 个新形状会让 `ItemIcon.tsx` 源码增大 ≈2.4 KB raw / 763 B gzip，
  不影响 `dist` 的其余分片。
- **CI 成本**：`check-assets.mjs` 是零依赖纯 node 脚本，扩容不增加其运行时间量级。
