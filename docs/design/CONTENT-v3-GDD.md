## 1 · 设计目标与一句话主张

### 1.1 本轮要解决的问题

v2.0.0 上线时有三处内容是「结构有、货没填」：

| 缺口 | 现状 | 本轮补什么 |
|---|---|---|
| 阶段 3 目标链 | `STAGES[2].steps = []` | 3 步目标链（能造出东西），3 个全新 mid 产物 |
| 第四条支线 | `BRANCHES` 只有 ship / teashop / birthday | 第 4 条支线「留下来」+ 三槽位 + 6 个 commission 候选 + 新结局 `stay` |
| 前任叙事 | 只有零散的环境叙述，没有「飞船为什么坠毁」的答案 | 8 篇前任日志（复用既有 kind，载体即物品） |

外加一条二周目（New Game+）的**规则设计**（不 bump `schemaVersion`）。

### 1.2 设计目标（按优先级）

1. **不破坏既有 36 条配方与 4 个结局的可达性**——任何新增的阶段目标标签对，都不得被任何现有配方的材料并集覆盖。
2. **让「留下」成为一件可被物证支撑的事**——第四支线三个槽位必须都是「具体物品」，不能是标签，不能是心情。
3. **前任日志必须是能被合成的物品**——不新增 kind，不新增交互形态，载体进背包、内容进日志面板。
4. **二周目零存档风险**——不 bump `schemaVersion`，不写迁移函数，老存档缺字段时归一化（T7 引导先例）。

### 1.3 一句话主张

> **阶段 3 教你怎么造东西，第四支线问你愿不愿意被这个地方认下来；前任日志回答「我们为什么把石头留在了这儿」；二周目让你带着这些答案再来一次。**

## 2 · A 线 · 阶段 3 目标链「建设期」

### 2.1 目标链逐步表

阶段 3 名称沿用 `建设期`，blurb 需要改一句（现状「接下来做什么，你自己定」与目标链冲突）→ 建议改为 **「能造出东西了。接下来造什么，你定。」**

| 步骤 id | requires（标签**并集**） | 标签来源数（池内） | output | 同构精确配方（材料对） | 主题 |
|---|---|---|---|---|---|
| `s3-1` | `['粘', '知识']` | 粘 4 / 知识 6 | `notice` **手写告示**（mid） | `tape` + `manual` | 把你在这儿这件事挂出去，让路过的人知道 |
| `s3-2` | `['金属', '能烧']` | 金属 3 / 能烧 4 | `generator` **手摇发电机**（mid） | `crowbar` + `fuel` | 有了能量，就有了「可以持续做下去」的能力 |
| `s3-3` | `['能推', '抽象']` | 能推 3 / 抽象 7 | `hourglass` **时漏**（mid） | `echo` + `broom` | 造一个能计时的东西，替你回答「还剩多少时间」 |

**弧的落点**：三步走完，玩家手上有了「被知道的告示 / 持续的电力 / 计时的沙漏」——正好对应支线的三条岔口：

- 有了告示 + 摊架 → 能开奶茶店、能让外星人知道你在这儿；
- 有了发电机 + 工具 → 能造飞船、也能留住一个摊子；
- 有了时漏 → 你终于能算「还待了多久」，也就终于能决定走还是留。

**「同构精确配方」是刻意设计的**，与上游 `windbreak`（`plunger`+`sock` ≡ s2-1 实体+实体）、`bedframe`（`screw`+`windbreak` ≡ s2-2 金属+实体）、`shelter`（`bedframe`+`lottery` ≡ s2-3 风险+实体）同构。好处有三：

1. `check-content.mjs` 断言 A（无孤立物品）要求每个非 accident/keepsake 物品都被配方引用——阶段 output 若没有精确配方就是孤立物品；
2. `playthrough.test.ts` 的闭包可达性算法只从 base 起经 **RECIPES** 推，阶段 output 不在闭包里——所以**以阶段 output 为材料**的配方会破坏可达性，而**阶段 output 自己**必须有一条从 base 可达的精确配方；
3. 玩家在阶段 3 之前也能用同一对材料造出这三样东西（标签机制允许），形成「提前备料」的玩法空间。

### 2.2 阶段 3 × 配方截胡核对表

**判定模型**（`resolve.ts:61`）：阶段目标优先于精确配方。`requires` 的标签**并集 ⊇ 玩家两件材料的标签并集**即命中阶段目标并**吃掉**配方产物。所以核对的口径是：

> 对每一步的 `requires` 标签对，遍历**全部配方**（既有 36 + 新增 23 = 59 条）的材料标签并集，若某条配方的并集**同时包含**该标签对，则这条配方的产物在走到该步骤时会被抢走。

**实测结果**（脚本枚举，产物与阶段 output 相同的三条同构配方除外）：

| 步骤 | requires 标签对 | 被覆盖的配方数 | 其中产物属支线 | 判定 |
|---|---|---|---|---|
| `s3-1` | 粘 + 知识 | **0** | 0 | ✅ 零风险 |
| `s3-2` | 金属 + 能烧 | **0** | 0 | ✅ 零风险 |
| `s3-3` | 能推 + 抽象 | **0** | 0 | ✅ 零风险 |

**这比工程要求更强**：工程只要求「不截胡支线产物配方」，本方案做到了**不截胡任何一条配方**（既有 36 条全部零覆盖）。

**output 与第四支线槽位是否重叠**：

| 阶段 3 output | kind | 第四支线槽位候选 kind | 是否重叠 |
|---|---|---|---|
| `notice` / `generator` / `hourglass` | `mid` | 全部 `commission` | ✅ 物理上不相交 |

**结论**：阶段 3 目标链对既有 36 条配方、新增 23 条配方、4 条支线的 23 个槽位产物**零截胡**。

**跨区域提醒（与 §9 R14 呼应）**：标签对本身零截胡 ≠ 标签在单一区域可得。实测（详见 §10.3）：`s3-1`（粘+知识）可在 crash/market 单区凑齐；`s3-2`（金属+能烧）需回 crash/junkyard；**`s3-3`（能推+抽象）没有任何单一区域能凑齐，必然跨区**。这不是软锁（`distribute` 硬保底本就跨已解锁区域搜，stage 3 时四区全解锁），但缺区域提示 → 见 R14 缓解 (a)+(b)。

### 2.3 标签选取的摘要

完整的档位表、备选组与「断言 E」建议在 **§10**。此处只给结论：

- 三步共 6 个标签位 = {粘, 知识, 金属, 能烧, 能推, 抽象}，**互不重复**；
- 池内来源数最紧的三个标签（`导电` 3 / `金属` 3 / `能推` 3）里，本方案只用了 `金属` 与 `能推`，**各只出现一次**，`导电` 不用；
- `s3-3` 选 `能推+抽象` 而非 `风险+能推` 的理由：两者都在工程零风险白名单内，但 `抽象` 池内来源 7 个（`风险` 只有 5 个），且玩家用抽象材料合成不会触发 `resolve.ts` 的风险兜底（`风险` 标签的材料一旦没命中配方就直接变 `failedtaste`），体验更顺。

### 2.4 阶段 3 三步走完后的归宿（拍板结论）

**结论：不进入 stage 4，也不进入任何新阶段；stage 保持 3，转入「建设期完成」态。**

理由三条：

1. **stage 4 在全代码里没有任何产生点**（`types.ts` 只有类型预留）。如果本轮把 stage 3 走完推成 stage 4，玩家会进入一个**内容为空**的阶段——没有目标链、没有支线、没有可做的事。这比「多一个阶段」严重得多。
2. **阶段 3 的语义本来就是「接下来做什么你自己定」**。给它接一条目标链已经是本轮的扩展（让「建设」有可感知的进度），再接一个新阶段等于把玩家的自由再切一刀。
3. **工程改动面最小**：`state.ts` 现在的阶段跃迁分支只处理 `stage === 1 || 2`；stage 3 走满后不需要新的跃迁分支，只需要「不再推进 stepIndex、解锁第四支线可见性」。

**玩家看到什么 / 能做什么**：

| 时刻 | 玩家可见 | 玩家可做 |
|---|---|---|
| 完成 `s3-1` | 目标链进度 1/3，`notice` 进背包，AI 点评「现在路过的人知道这儿有人了」 | 继续造、继续捡、随时可走支线 |
| 完成 `s3-2` | 进度 2/3，`generator` 进背包 | 同上 |
| 完成 `s3-3` | 进度 3/3 → **「建设期完成」横幅**（新 `DIALOGUE.clear3`，3 句）+ 目标链区折叠为「已建成」 | 第四支线「留下来」**正式对玩家可见** |
| 建设期完成后 | 目标链区显示「已建成：告示 / 发电机 / 时漏」 | 四条支线全部可选；仍可自由捡垃圾、合成；`free` 结局入口常驻 |

**为什么第四支线要等建设期完成才可见**：第四支线的三个槽位是「落脚 / 营生 / 熟人」——**都得有东西才谈得上**。如果在阶段 3 开头就亮出来，玩家会得到「我还什么都没有 → 我就走吧」的挫败结论。挂在「你已经造出东西了」之后，第四支线才是「有了资本之后选择留下」而不是「反正没事干就留下」。

**工程影响面（不落码，供工程评估）**：

- `state.ts`：阶段跃迁分支新增 `stage === 3 && stepIndex >= STAGES[2].steps.length` 的情形 → **不改变 `stage`**，只写一条 `阶段` 日志、置 `stepIndex = 3`、发 `STAGE_KEEPSAKES[3] = 'ks_build'` 纪念品、置一个 `buildDone` 语义位。
- `buildDone` 语义位**不 bump `schemaVersion`**：按 T7 先例，作为新增字段写入 v2 存档并在读档时归一化（老档缺字段 → `false`）。
- `resolve.ts`：`progress.stage === 1 || 2` 的阶段目标判定分支需要扩到 stage 3（`stepIndex < 3` 时才判阶段目标；`stepIndex >= 3` 后阶段目标不再拦截，回归纯配方判定）。
- `search.ts`：`missingForBag` 当前**只处理 stage 1/2**。阶段 3 的 `粘/知识/金属/能烧/能推/抽象` 全部有池内来源，但**不会触发硬保底** → 玩家可能反复搜不到材料而卡住。**必须把硬保底扩展到 stage 3**，否则本轮目标链存在软锁风险（见 §9 风险 R1）。
  > **落点纠正（2026-10-21）**：v2 已删「搜索」动作，`searchArea` / `pickSearch` 在 web 端调用点为 0（v1 遗留死路径）；**硬保底的落点由 `world.ts` 的 `distribute` 负责**（它已跨已解锁区域并集），`missingForBag` 的职责收窄为「判定玩家还缺哪些标签」这一纯函数。跨区域**提示**落在 HintBar（web 端），详见 §8 约束 4 与 §9 R14。

### 2.5 「自由模式」口径（拍板结论）

**结论：`free` 结局 = 「完成迫降期（`stage ≥ 2`）之后随时可选，且永久可选」。**

| 时点 | `free` 是否可选 | 理由 |
|---|---|---|
| 第 1 天（stage 1） | ❌ 不可选 | 玩家还没学会合成、还没理解标签并集就能「结束游戏」，等于把游戏的核心机制变成可跳过项 |
| 完成阶段 1（stage ≥ 2） | ✅ 可选 | 玩法已被理解，「我要就这样收摊」是一个**有意义**的选择而不是逃避 |
| 完成任一支线后 | ✅ 可选，且与其他结局并列 | 支线结局是「你做到了 X」，`free` 是「你什么都不再追求了」——两者不冲突 |
| 完成第四支线（stay）之后 | ✅ 仍可选 | 语义分叉是刻意的：**「我建好了这里，但我还是想走」**。这比强制互斥更有意思 |
| 手动起飞失败后 | ✅ 可选 | 已有 `ks_fail` 纪念章作为「试过了」的交代 |

**这带来一个必须写进 SPEC 的口径修正**：SPEC §4.1 写的是「完成任一支线 → 自由模式」，与现状 `state.ts:363-371` 里 `free` 无条件 `push` 也不一致。建议把 SPEC 改写为：

> **自由模式**：完成迫降期后随时可选。支线结局在对应支线完成时解锁。完成支线不会关闭自由模式——**「留下来」和「走」永远同时可用**。

**工程影响**：`availableEndings()` 里 `free` 从无条件 push 改为 `state.stage >= 2` 时 push（老档 `stage` 字段本就存在，无需归一化）。**代码现状比本节结论与 SPEC §4.1 都更宽松**——`state.ts` 的 `availableEndings` 现在是 `out.push('free')` **无条件**，即 stage 1 就能选 free 结局。**批次归属：A2 批次实施**（与第四支线 `stay` 一起做，因为「stay 完成后 free 仍可选」这个语义要在同一处改）。工程影响清单见附录 B 第 10 条。

### 2.6 `DIALOGUE.stage3` 定稿台词（4 句）

**使用时机**：玩家在**阶段 3 首次解锁第四支线时**看到的引导性台词（不是结局台词）。

```
'接下来四条路：造飞船走人、开奶茶店、给石头过生日、留下来。',
'前三条是往远处走，最后一条是往这儿扎。方向正好相反。',
'我建议造飞船。另外三个都要有人配合，最后一个尤甚——它要的不只是东西。',
'哪条都行。我没有腿，也不出门，所以「留下来」这一条我没法反对。'
```

**设计说明**：

| 句 | 承担的职责 |
|---|---|
| 第 1 句 | **点全四条路**，顺序与支线面板一致（ship / teashop / birthday / stay），玩家在这一句里第一次看到「留下来」与前三条并列 |
| 第 2 句 | **方向反差**：前三条往远处、第四条往这儿扎。用「方向正好相反」收尾——比「往远处走」更强调这是一个**反向**，而不是第四条只是名字不同 |
| 第 3 句 | **AI 的倾向 + 差异提示**：保留「我建议造飞船」（导航员给建议，不替玩家做主）；后半句点出后三条都需要「有人配合」，而 stay 需要的不只是东西（伏笔：落脚 / 营生 / 熟人三个槽位里有「一个知道你在这儿的人」） |
| 第 4 句 | **冷幽默收束**：AI 没有腿也不出门，所以「留下来」是它唯一不反对的路。这句同时把反差坐实——第四条路是唯一一条「AI 也不需要离开」的路 |

**自查**：

- 四条路全覆盖 ✅；「第四支线方向相反」的反差由第 2 句 + 第 4 句双重承担 ✅；「我建议造飞船」保留且给了理由 ✅。
- **无 UI 味 / 系统味**：全文不出现「选择」「选项」「难度」「解锁」等词；第 4 句用「哪条都行」而不是「选哪条都行」。

### 3.4 第四支线与前三支线的关系

| 支线 | 三槽位 | 完成后的结局 | 语义 |
|---|---|---|---|
| ship 造飞船 | 动力 / 外壳 / 生命维持 | `leave` | 走 |

`stay` 与 `free` 的区别是**物证**：free 随时可选、不需要任何东西；stay 需要三件「这个地方承认你」的实物。`stay` 完成后 `free` 仍可选——那是另一个结局：「建好了，但我还是想走」。

### 3.5 第四支线完成时是否即刻进结局（拍板结论）

**结论：完成即进结局**，与 `teashop` / `birthday` 的现有规则（`state.ts:265`）保持一致。

工程侧建议「完成即进结局，但结局页提供二周目入口」，我确认，并补一条**工程侧没提但我认为必须有的**：

> 结局页需要**两个出口**，不是一个：
> - 「**开始二周目**」→ 走 §7 的重置流程，清空本局进度、保留纪念品与图鉴。
> - 「**留在这里继续**」→ **不清档**，回到自由模式（`free` 结局页的等价态），玩家可以继续捡垃圾、继续合成、继续待着。

理由：第四支线与 `free` 语义相邻，如果「完成 stay 只能二周目 / 走人」二选一，玩家会觉得「我只是想留下来，结果游戏结束了」。而如果只给一个出口，`free` 就在 `stay` 完成时变成不可达，等于用 `stay` 覆盖了 `free`——这比让两者并存要糟。

因此 `state.ts` 的规则要写成：**非 ship 支线完成 → 进结局页（不强制清档）**，由结局页决定下一步。ship 支线保持现状（玩家自己决定何时起飞）。

### 3.6 第四支线的可见时机

| 时机 | 可见性 | 理由 |
|---|---|---|
| 进入阶段 3 | ❌ 不可见 | 此时玩家一无所有，「留下来」在语义上是空的 |
| 完成阶段 3 三步（建设期完成） | ✅ 可见，出现在支线列表第 4 项 | 此时玩家手上已有告示、发电机、时漏——**有了可以被留下的资本** |
| 支线面板文案 | 「前三条路是往远处走，这一条是往这儿扎」 | 给一个方向提示，不解释具体是什么 |

**工程影响**：支线列表的可见性需要一个新字段（`BRANCHES[].requiresBuild?: boolean`）或按 `branch.id === 'stay' && !buildDone` 直接隐藏。**注意**：第四支线的**完成判定**从阶段 3 一开始就有效（`state.ts` 的支线检查只看 `next.stage === 3`），玩家如果在建设期完成前就集齐了三件 commission，也**能完成 stay**——这是好事，不做额外门禁（门禁只作用于**可见性**，不作用于**可达性**）。

### 6.2 解锁节奏

**混合三种条件**（按任务书要求：天数 / 阶段 / 合成次数）：

| L2 | `log_map2` | 天数 ≥ 9 | 「一张写满数字的表」 | 第 7 天 | 阶段 2 |
| L3 | `log_page2` | 天数 ≥ 12 | 「一天一段的册子」 | 第 8–11 天 | 阶段 2 |
| L4 | `log_map1` | **完成阶段 2** | 「一张被描破的图」 | 第 12 天 | 阶段 3 |
| L5 | `log_chip1` | 合成次数 ≥ 14 | 「一块还在发热的芯片」 | 第 14 天 | 阶段 3 |

**L4 解锁条件的对齐确认（自查项）**：`log_map1` 的配方是 `manual`+`mirror`（R19），`mirror` 在 **market**，而 market 的 `AREA_UNLOCK_STAGE = 2`（即 `stage ≥ 3` 才解锁）。L4 的解锁条件写「完成阶段 2」——阶段 2 完成的瞬间 `progress.stage` 由 2 变为 3，**market 在同一时刻解锁**。因此二者是**严格同时成立**的，L4 不会出现「已解锁但材料还在锁着的区域」的空窗。**这是有意的对齐，不是巧合**：把 L4 挂在阶段 2 完成点上，正好让「航路草图」与「进入建设期」在叙事上同时发生（前任画的是来时的路，玩家刚走到能画新路的地方）。**确认成立，保留现写法。**

### 6.2.1 `playerView` 的「不剧透标题」口径（2026-10-21 修订）

**规则**：日志面板有三态——`readable`（条件满足且载体已合成，显示标题 + 全文）/ `waiting`（条件满足、载体未合，显示标题 + 「还没找到「xxx」。」）/ `locked`（条件未满足，显示「**？？」+ `playerView`**，**不显示真实标题**）。`playerView` 是 locked 态唯一的可见文案，因此它**不得包含该篇的真实标题**，否则「不剧透标题」的设计意图被自己破坏。

**修订记录**：初版 L3 的 `playerView` 写作「**值班记录，一天一段**」——真实标题「值班记录」四个字原样出现在括号里，等于间接剧透。**已修订为「一天一段的册子」**（把标题换成对**载体形态**的描述：册子 / 一天一段），保留原本的钩子信息量、去掉标题泄漏。

**修订后的全 8 篇 `playerView` 与标题泄漏实测**（脚本逐篇比对「标题与 `playerView` 的最长公共子串」）：

| 序 | 真实标题 | `playerView`（locked 态显示） | 与标题的最长公共子串 | 判定 |
|---|---|---|---|---|
| L1 | 缺页手稿 | 「有一页纸从设备里掉出来」 | `页`（1/4） | ✅ 无标题泄漏 |
| L2 | 燃料清单 | 「一张写满数字的表」 | 无 | ✅ |
| L3 | 值班记录 | 「**一天一段的册子**」（修订后） | 无（修订前为「值班记录」= 全称泄漏） | ✅ **本轮修订** |
| L4 | 航路草图 | 「一张被描破的图」 | `图`（1/4） | ✅ |
| L5 | 存储芯片 | 「一块还在发热的芯片」 | `芯片`（2/4） | ✅ 可接受——「芯片」是**载体形态**（一块发热的电路），不是「存储」这个内容信息；标题里真正带信息量的是「存储」，未泄漏 |
| L6 | 未完的问句 | 「一个没写完的问句」 | `完的问句`（4/5） | ✅ 可接受——「问句」是**载体形态**（纸上写了个问句），带信息量的是「未完」；`playerView` 里的「没写完」正是内容钩子本身，属有意 |
| L7 | 前任遗物 | 「一个热着的旧物」 | `物`（1/4） | ✅ |
| L8 | 数据卷盘 | 「最后一卷录音」 | `卷`（1/4） | ✅ |

> **判定标准**：泄漏的是**标题里承载内容信息的那部分**，而不是**描述载体形态的通用词**。「芯片」「问句」「册子」都只是「这是一个什么东西」的形态描述；玩家看到「一块还在发热的芯片」时不知道它**存了什么**、看到「一个没写完的问句」时不知道那个问句**是什么**——这正是 locked 态该给的信息量。**真正要避免的是「值班记录」这种把标题整词照抄的情况**（它把「这是关于某段时间值班的内容」一并说了）。

> **边界声明**：本节只管 `playerView`（面板文案）。**载体物品名**（`items.ts` 里 `log_page2` 的 `name` 仍是「值班记录」）在玩家合成出载体、物品进背包后必然可见——这是**另一层**的设计取舍：载体是**实物**，玩家捡到的东西有名字是合理的，且它要到玩家真的凑齐 `manual`+`broom` 才会出现。若将来要把「实物名」也藏起来，需要在 `items.ts` 里给载体一套与日志标题解耦的别名（例如「一本翻旧了的册子」），那是**新的一轮内容改动**，本轮不涉及。


**解锁实现建议**：解锁条件挂在**日志条目的可见性**上，不挂在物品获取上——即 `LOGS` 表每条带 `unlock: { day?, crafts?, stage?, step? }`，读档/进天时统一计算。载体物品本身是普通合成产物，捡到/合出即进背包。

### 6.4 碎片顺序与拼合点

**顺序**：玩家按 §6.2 的解锁顺序读到 L1→L8；L1–L8 内部是前任的时间序（第 1 天 → 第 21 天），两套顺序一致，不会出现「先读到后面的事」。

**拼合点**（读到第 N 篇时才揭示的东西）：

> **拼合点的定义（本节判定依据）**：一条拼合点 = 玩家读到第 N 篇时，把**「本篇提供的新信息」**与**「此前某一篇里的旧信息」**合并，因而能读出的**一条此前没有明写出来的新结论**。
>
> 三条硬要求：
>
> 1. **必须跨篇——结论不能被任一单篇独立支撑。** 它需要两篇的信息合起来才成立（其中一篇提供新端，一篇提供旧端）。单篇正文自己已经明写的内容，**不是**拼合点（那是正文）。注意「跨篇」不等于「两端各有一半字面」：旧端的作用常常是**让新端的指代成立**（例：P2 的新端在 L4 说「它唱歌的次数与余量正相关」，但「它」是石头这件事要到 L3 才建立——没读 L3，L4 的「它」无所指）。
> 2. **必须有增量——读到本篇之前，玩家无法完整说出这条结论。** 若这个结论在本篇之前就已经能读出来，那它不是「揭示」，是复述。
> 3. **触发篇必须是提供新端的那一篇**——即合并真正发生的那一篇。挪到别的篇次去，「读到这篇时合并出一条新结论」这句话就不成立。
>
> 按这三条判定，8 篇里成立的拼合点是 **P2 / P3 / P4**（见下表）。**P1 不成立，已取消**（原因见本节末的修订说明）。

| 拼合点 | 触发 | 揭示内容 | 玩家此时知道 | 跨篇的两端 |
|---|---|---|---|---|
| **P1** | — | **已取消**（原挂 L2，不构成拼合点） | — | 原两端都在 L1 之内，L2 不提供任何一端 |
| **P2** | 读到 L4 | 「坠毁不是事故，是主动降落；石头会唱歌，唱歌次数与物资余量正相关——它在报数」 | 降落是选择；石头是主动留下来的关键 | 新端 = L4「迫降是选出来的 / 它在报数」；旧端 = L3「石头每天唱 11 遍，多一遍算异常」 |

【任意结局页】 leave / teashop / birthday / stay / free
      │

**图鉴入口**：主菜单与结局页各一个「**图鉴**」入口，页内两栏：

**二周目解锁条件**：完成任意一个结局后，二周目入口才出现（`ngPlus.cycle >= 1` 且 `ngPlus.endings.length >= 1`）。**一周目内不可见**——避免玩家在还没玩明白时把「重开」当成「跳过」。

**📌 结局页入口已区块化（2026-10-22 · 方案已批准，代码待工程落地）**：本流程的**判定与步骤不变**（按钮位置、出现条件、确认页三段、`cycle += 1` 的写入时机全部不动），改的是**入口的可见性与措辞**：
- 结局页上那个二周目按钮由「裸按钮」改为**有标题的区块**——小标题「带着记忆再来一遍」+ 说明行「地面上的东西会回到原位。你记得的会留下来。」+ 按钮「**再走一遍**」（原「开始二周目」/「开始新的周目」作废；**「二周目」是内部术语，不进玩家可见文案**）。

### 7.2.2 「留在这里继续」后再次进入 stay 结局：结论为**不做 UI 提示**（2026 复审拍板）

**现象**：`continueAfterEnding()`（`packages/game-core/src/ngplus.ts`）只清 `ending`，`branches.stay` 仍为 `true`。回到自由模式后，支线面板的「留下来」按钮仍在（`branches.stay` 为 true 就显示），玩家再点一次 → `chooseEnding('stay')` → 再进一次 stay 结局页 → 再点「留在这里继续」→ 再回自由模式。**什么都没变。**

**core 侧无缺陷**（QA §2.3 C-2 实测）：`craft()` 的支线检查是 `if (status.done && !next.branches[status.id])`（`state.ts`）→ 不重复写 `ending`、不重复发纪念品、不重复 `recordEnding`（后者本身幂等）。**数据一致，语义自洽**（支线面板显示「本周目完成」是事实描述）。

**拍板：不做 UI 提示。** 五条理由：

| # | 理由 |
|---|---|
| 1 | **信息已在决策点给过了。** 支线面板在「留下来」按钮旁已经标「本周目完成」（`BagDrawer.tsx`）——玩家**点之前**就知道这条已完成。结局页再重复一遍是纯噪音 |
| 2 | **按钮语义是「去看这个结局」，不是「领取奖励」。** 再次进入看到同一个结局，与按钮字面一致，不构成「错乱」——像重读一章，不是出错 |
| 3 | **没有需要解释的状态异常。** 提示的正当用途是解释「看不懂的状态」；而这里既不丢东西也不改状态，玩家不需要被解释 |
| 4 | **避免暗示「必须留」。** stay 与 free 在自由模式下是**并列可选**的语义分叉（§3.4：free =「什么都不再追求」，stay =「这个地方承认了你」）。加一句「这一支线已经算完成」会读成「留下是一次性的、不可逆的决定」，抬高 stay 的分量、破坏两者并列 |
| 5 | **纯 free 结局的重复进入是常态，不该被当成异常。** `free` 在 `stage >= 2` 时**永久可选**（`state.ts` 的 `availableEndings`），玩家反复进入 free 结局页是设计内的正常行为。只针对 stay 加提示，等于把一个通用行为当成特例 |

> **⚠️ 若将来仍要做提示，先解决这个技术陷阱**：`save.branches[ending] === true` **在首次通过 craft 达成 stay 的那一刻就已经为 true**（支线达成与写 `ending` 是同一次提交，见 `state.ts` 的支线检查块）。以它为条件会让**第一次**看到 stay 结局页时也弹出「已经完成」，把一次成功的达成说成重复——比不提示更糟。真要做，必须另设**瞬时标志**（如由自由模式面板触发的 `chooseEnding` 路径才置位），而不是读存档字段。
>
> **确认页（`NgPlusConfirm`）不是这个问题的位置**：那一页讲的是「开新周目会失去什么」，与 stay 残留无关，不要往那里加。


### 7.2.1 `DIALOGUE.ngplus` 定稿台词（3 句）

**使用时机**：二周目第 1 天、回到坠毁点时播放的开场。

```
'又见面了。这一次信号器还是坏的，但你知道它坏在哪儿。',
'世界是新的——地面上的东西都回到原位，只有你带着记忆回来。',
'纪念品我替你收着。别的都重新来，包括那些你本来能省下的麻烦。'
```

**设计说明**：

| 句 | 承担的职责 |
|---|---|
| 第 1 句 | **重逢感 + G3「你认得路」**：用「信号器」这个一周目的具体物做锚点（它还是坏的，但你**知道**坏在哪儿）——「你认得路」不靠抽象抒情，靠一个具体的技术事实落地 |
| 第 2 句 | **核心体验一句话**：**世界是新的 / 你不是**。后半句把「世界进度清零但你记得路」这条二周目主体验说尽，且不涉及任何具体内容或奖励（不剧透） |

**自查**：

- 3 句 ✅；覆盖 G3「你认得路」（第 1 句 + 第 2 句）✅；提到纪念品保留 ✅；**不剧透**二周目的具体内容与奖励 ✅（没提支线、没提日志提前解锁、没提任何具体道具）。
- **不煽情**：第 1 句的「又见面了」是陈述，不带情绪形容词；第 3 句的「麻烦」是吐槽语气（吐槽事情不攻击玩家）。全篇没有「终于」「等着你」「我们」这类煽情或拉关系的词。

### 7.3 字段语义（不 bump `schemaVersion`）

**硬约束**（工程已确认）：web 层 `SAVE_SCHEMA = 2`，`readSavedGame()` 对 `schemaVersion !== 2` 直接返回 `null`（丢弃存档、不写迁移）。契约 §3.1 明确「非 2 直接丢弃」。因此：

> **二周目绝不允许 bump `schemaVersion`。** 一旦升到 3，所有 v2 存档在下次打开时被直接丢弃 = 玩家一周目进度全灭。

**落地方案：T7 引导先例**——`tutorial` 字段当初就是**新增字段但不 bump**，读档时 `readTutorial()` 归一化（缺字段 → `TUTORIAL_SKIP`）。二周目沿用同一模式。

**新增字段（挂在现有 v2 存档对象上，全部可选）**：

> **⚠️ 实施现状注记（2026-10-21，team-lead 记账）**：下表描述的是 **C2 批次的目标形态**，不是 A2 批次的已实现状态。A2 批次实际只落了布尔语义位 **`ngPlus: boolean`**（因为「字段入类型 + 读档归一化、不 bump `schemaVersion`」这条先例在 A1a 刚立过，先把语义位占住）。**C2 批次会把它扩成下表的 `NgPlusState` 对象容器**，届时老存档里那个 `true` 会被当作「`cycle ≥ 2` 的空档案」归一化（见下方 `normalizeNgPlus` 伪码）。**该迁移点已写进代码注释与 C2 任务书**，本 GDD 不重复定义迁移实现，只声明目标形态。

| 字段 | 类型 | 语义 | 缺省值（归一化后） |
|---|---|---|---|
| `ngPlus` | `NgPlusState \| undefined` | 二周目档案总容器 | `undefined` → 归一化为下方默认值 |
| `ngPlus.cycle` | `number` | 已完成的周目数（1 = 一周目进行中/已结束） | `1` |
| `ngPlus.endings` | `EndingId[]` | 已解锁结局集合（去重） | `[]` |
| `ngPlus.readLogs` | `string[]` | 已读日志条目 id 集合（去重） | `[]` |
| `ngPlus.branchesHistory` | `BranchId[]` | 曾经完成过的支线（用于 G3 提示） | `[]` |
| `buildDone` | `boolean` | 阶段 3 三步是否已完成（用于第四支线可见性，§2.4） | `false` |

**归一化函数**（建议放在 web 层 `gameStore.ts`，与 `readTutorial()` 并列，或放 game-core 内的纯函数 `normalizeNgPlus(raw)`）：

```
normalizeNgPlus(raw):
  np = raw?.ngPlus ?? {}
  cycle            = int(np.cycle) >= 1 ? int(np.cycle) : 1
  endings          = uniq(filter(np.endings, e ∈ {leave,teashop,birthday,stay,free}))
  readLogs         = uniq(filter(np.readLogs, s ∈ LOG_IDS))
  branchesHistory  = uniq(filter(np.branchesHistory, b ∈ {ship,teashop,birthday,stay}))
  buildDone        = raw?.buildDone === true
  → 写回同一份 v2 存档，schemaVersion 保持 2
```

**为什么这样安全**：

1. `schemaVersion` 保持 2 → 现有 v2 存档**继续被读取**，不触发丢弃。
2. 老存档缺 `ngPlus` / `buildDone` → 归一化补默认值 → 玩家进入游戏即拥有 `cycle: 1`、`endings: []`、`buildDone: false`，**与一周目体验完全一致**。
3. 归一化是**纯函数 + 幂等**，每次读档执行一次即可，不产生迁移链。
4. `buildDone` 与 `ngPlus` 是**同一次读档里的两个新增字段**，共享同一套「缺字段 → 默认值」的模式，工程上是一处改动。

**`EndingId` 枚举扩展**：`types.ts` 的 `EndingId` 需从 4 个扩到 5 个（加 `stay`），`BranchId` 从 3 个扩到 4 个（加 `stay`）。这是**类型层扩展，不是存档格式变更**——存档里 `branches` 是 `Record<BranchId, boolean>`，老存档缺 `stay` 键时：

```
readBranches(raw.branches) = { ship: !!raw.branches?.ship, teashop: ..., birthday: ..., stay: !!raw.branches?.stay }
```

**`branches` 字段的归一化必须做**：否则 `next.branches[status.id]` 在 `status.id === 'stay'` 时写入 `undefined` 键，UI 读 `branches.stay` 得到 `undefined`（falsy，功能上不炸，但 `availableEndings` 的汇总与云端同步会拿到不一致的形状）。归一化后老档读出来是 `{ ship:false, teashop:false, birthday:false, stay:false }`，与 `createInitialState()` 的形状一致。

**云端同步**：`cloud.ts` 的 `branches` 类型与 `progressScore` 需要同步加 `stay` 分支（`progressScore` 是否给 `stay` 计分 → **建议计分，权重与 `teashop` / `birthday` 相同**）。**实施时点后移**（2026-10-21 记账）：`progressScore` 是否给 `stay` 计分，改由专门的「**支线计分批次**」统一做，避免云端分数口径在批次中间漂移。**本 GDD 的建议保持不变**，只是实施时点后移。

### 7.4 玩家在二周目里的实际体验差异（一句话）

> 一周目：你在一个陌生星球上从零开始；二周目：你带着「已经知道这里发生过什么」的记忆重新开始——**世界是新的，但你不完全是**。

### 7.5 二周目是否保留纪念品（拍板结论）

**结论：保留全部纪念品（`keepsakes`），包括上一周目得到的。**

理由三条：

1. **纪念品不参与任何判定**。`keepsake` 类物品「只陈列不参与合成」（`items.ts` 注释），也不出现在任何 `BRANCH.requires` / `STAGES[].steps.output` 里。保留它**不产生任何数值优势**。
2. **清空会直接杀死二周目的动机**。二周目的核心期待是「这次我能不能把上次没拿到的都拿到」。如果每次重开纪念品清零，玩家的心理模型会变成「收集只在单周目内有效」，图鉴也就失去了跨周目的意义。
3. **纪念品的发放是幂等的**。`state.ts` 现有逻辑是 `keepsakes.includes(keepsake) ? keepsakes : [...keepsakes, keepsake]`——重做同一支线**不会重复发放**，所以「保留 + 重做」天然不会出现重复条目，不需要额外去重逻辑。

**例外与提醒**：

| 项 | 处理 |
|---|---|
| 二周目重做同一支线的纪念品 | 不重复发放（现有 `includes` 判断已保证） |
| `ks_build`（建设纪念牌） | 二周目重做阶段 3 才会再发一次，同样幂等 |
| 二周目**新增**的纪念品 | 若后续版本新增纪念品类型，二周目可作为「补齐收藏」的来源——这是保留策略的额外收益 |
| 玩家想看「干净的一周目」 | 提供「清空纪念品」开关（默认关闭）。**不作为默认行为**，因为默认清空就是伤害收集欲的那一方 |
