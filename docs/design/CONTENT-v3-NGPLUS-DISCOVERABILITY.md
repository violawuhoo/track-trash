# C2 批次 · 二周目入口可发现性方案

> **文档性质**：设计侧方案（**只出文档，不碰源码**）。
> **作者**：文策渊（design-strategist）｜**日期**：2026-10-22
> **触发**：engineering-lead-3 提出「残留的真实风险不在『重复进入提示』，而在**二周目入口的可见性**——玩家如果不知道『二周目』的存在，『留在这里继续』就等于唯一出口」。
> **授权范围**：不改动判定（不改 `ngPlusUnlocked` 解锁条件、不改结局分支）、不新增「搜索」类机制。
> **代码真源**：`packages/game-core/src/ngplus.ts`（`ngPlusUnlocked`）、`apps/web/src/screens/EndingScreen.tsx`、`apps/web/src/components/NgPlusConfirm.tsx`、`apps/web/src/screens/StartScreen.tsx`、`apps/web/src/store/gameStore.ts`。
> **本文档不是定稿**：§5 的落地清单与 §3 的文案定稿需要用户拍板后才交工程。

---

## 0 · 一句话结论

**入口在实现上是「存在且能到达」的，但它是「一次性曝光 + 零解释 + 视觉权重低于同屏 primary 按钮」——玩家大概率看得见按钮、看不懂它是什么、并且错过之后没有任何再曝光的机会。**

推荐方案 = **三处轻改，全部不改判定**：

| # | 改动 | 成本 | 作用 |
|---|---|---|---|
| **A** | 结局页把入口从「裸按钮」提升为**有标题的区块**（标题 + 一行说明 + 按钮） | 小（一个 div + CSS） | 让玩家**看懂**它是什么 |
| **B** | 主菜单（`StartScreen`）在已解锁时给一个**次级文字入口** | 中（需处理主菜单无活动存档的问题，见 §5.3） | 让玩家**错过之后还能回来** |
| **C** | 「再来一次」与「开始二周目」**改名区分**（语义相邻，有误读风险） | 极小 | 消除误读 |

否决：奖励化呈现、结局页把入口升为 primary、主菜单放并列大按钮、反复 toast 宣传、自动弹窗、图鉴内藏入口、提前解锁条件。

## 1 · 现状调研（实读代码）

### 1.1 入口实际位置：只有一个，在结局页

全站搜索 `ngPlusUnlocked` / `开始二周目`，消费点只有两处：

| 文件 | 行 | 内容 |
|---|---|---|
| `apps/web/src/screens/EndingScreen.tsx` | `:91` | `const canStartNgPlus = ngPlusUnlocked(archive);` |
| `apps/web/src/screens/EndingScreen.tsx` | `:132-140` | 条件渲染按钮 |
| `apps/web/src/components/NgPlusConfirm.tsx` | `:149` | 确认页（`openNgPlusConfirm` 由结局页按钮触发） |

**主菜单 `StartScreen.tsx` 没有任何二周目入口**。`:84-97` 的按钮列只有三个：`开始游戏 / 重新开始`（primary）、`继续游戏`（有存档时）、`图鉴`。

**图鉴 `CodexPanel.tsx` 里也没有**。图鉴是跨周目容器（主菜单与结局页都能开），头部只有一行统计：`:137` → `结局 {unlockedEndings} / 5 · 日志 {readCount} / 8`。

### 1.2 出现条件

```ts
// packages/game-core/src/ngplus.ts:141
export function ngPlusUnlocked(np: NgPlusState): boolean {
  return np.cycle >= 1 && np.endings.length >= 1;
}
```

- `cycle` 口径为「当前周目序号」，`createNgPlus()` 给 `cycle: 1` → `cycle >= 1` **恒真**。
- 真正的闸门是 **`endings.length >= 1`**——即「至少完成过一个结局」。
- 完成结局时 `finishGame()` → `recordEnding()` 写入 `ngPlus.endings` → `commit()` 同步 `archive` → 进入结局页时 `archive.endings.length` 已 ≥ 1。
- **结论：玩家达成第一个结局的那一刻，入口就在那屏上出现。** 不存在「一周目内完全看不到」的情况。

### 1.3 视觉权重：普通按钮，且被 primary 按钮压在下面

结局页按钮列（`EndingScreen.tsx:119-157`，自上而下）：

```
[留在这里继续]        btn btn--primary btn--block   ← 仅 stay / free，有强调色
[开始二周目]          btn btn--block                 ← 无强调、无标题、无说明
[图鉴]                btn btn--block
[再来一次]            btn btn--block
[回到开始页]          btn btn--block
```

- 二周目入口是**四五个同款灰按钮中的一个**，没有 `btn--primary`、没有标题、没有副文案。
- 它排在 **primary 的下面**——视线落在第一个按钮上是常态。
- 文案只有四个字「开始二周目」（`cycle >= 2` 时改「开始新的周目」），**零解释**。

### 1.4 确认页的信息量其实很足

`NgPlusConfirm.tsx` 标题「开始新的周目」+ 副标「第 N 周目 · 带着记忆再来一遍」，三段：**保留**（5 条，含计数）/ **重置**（8 条）/ **本周目增益**（G1–G4）。

**结论：教育成本不在确认页，在入口那一屏。** 玩家只要点进来就会明白；但如果他不知道可以点进来，确认页再完美也没有用。

### 1.5 玩家能不能走到结局页

能，而且成本不高：

- `BagDrawer.tsx` 收尾区在 `stage >= 2` 常驻「**自由模式**」按钮（`chooseEnding('free')`）→ 随时可进 free 结局页。
- `teashop` / `birthday` / `stay` 三条支线完成后各自有按钮。
- `leave` 走起飞。

**所以「玩家走不到结局页」不是真问题**（engineering-lead-3 担心的「结局只有 stay/free 两条路」在实现上不成立——`free` 是常驻的）。

### 1.6 错过之后还有没有第二次机会

这是**真问题**。入口的曝光窗口 = 「玩家正站在结局页的那几秒」，而结局页有 5 个按钮，玩家点完就走。此后：

| 玩家在结局页点了 | 落到哪 | 还能再看到「开始二周目」吗 |
|---|---|---|
| 「留在这里继续」 | 回自由模式 | **能**——`free` 常驻，再点一次即可回到结局页 |
| 「再来一次」 | `newGame` → 回到**当前**周目第 1 天 | **不能直接看到**——必须重新达成一个结局才能再见到入口 |
| 「回到开始页」 | 主菜单 | **不能**——主菜单无入口（图鉴也没有） |

**真正的「入口存在但玩家永远看不到」的情形**：玩家达成第一个结局 → 点「回到开始页」 → 之后只玩「继续游戏」或直接不再玩这个周目。**在这个路径上，玩家永远不会再看到二周目入口**（除非他碰巧又去自由模式触发一次结局）。

这是需要修的。

## 2 · 问题诊断

| # | 症状 | 证据 | 后果 | 严重度 |
|---|---|---|---|---|
| **D1** | **曝光窗口只有一次，且是「结局页的 5 个按钮之一」** | `EndingScreen.tsx:119-157` | 玩家错过 = 永久错过（走「回到开始页」路径时） | **高** |
| **D2** | **按钮零解释** | `:138` 只有「开始二周目」四字 | 玩家不知道它是「重来一遍」；中文语境里「二周目」易被读成「后续内容 / 更高难度」 | **高** |
| **D3** | **视觉权重低于同屏 primary 按钮** | 二周目在「留在这里继续」之下、无 `btn--primary` | 视线先落在第一个按钮，入口被跳过 | 中 |
| **D4** | **「再来一次」与「开始二周目」语义相邻、名字易混** | 两个按钮紧邻，都读作「再玩一次」，但一个是重置本周目、一个是开新周目 | 玩家**误以为**「再来一次」就是二周目 → 点错 → 得到一个不带记忆的周目 → 反而认为二周目没用 | 中 |
| **D5** | **图鉴在主菜单可开，却不透露「可以再走一遍」** | `CodexPanel.tsx:137` 只显示 `结局 1/5` | 玩家在主菜单看图鉴时会意识到「还有别的结局」，但没有任何东西把这件事和「重走一遍」连起来——**这是离入口最近的一次未使用的曝光位** | 中 |
| **D6** | 入口与「解锁」语义耦合导致玩家误判前置条件 | `ngPlusUnlocked` 要求先有一个结局 | 玩家若以为「必须先通关」就永远不会尝试——**但这是设计意图（代码注释：避免把重开当成跳过）**，不是缺陷 | 低（**不改**） |

## 3 · 方案

### 3.1 推荐方案（改动判定：零）

#### A. 结局页：把入口提升为**有标题的区块**（推荐）

不把它做成别的按钮，而是给一个**自己的小标题 + 一行说明**：

```
┌ 结局正文 / 统计 …

[留在这里继续]                 ← 仍是 primary，位置不动

  带着记忆再来一遍                ← 新增小标题
  地面上的东西会回到原位。你记得的会留下来。
  [ 开始二周目 ]                  ← 按钮保留原样

[图鉴]
[再来一次]
[回到开始页]
```

**为什么这是首选**

1. **解决 D2 / D3，且不需要新增任何机制**——纯展示层。
2. **不违反「不得暗示必须走二周目」**：它不是按钮列表里多出来的一个可选动作的同义词，而是一块**被解释过的区域**；说明文案讲的是「会发生什么」，不是「你应该去」。
3. **不违反「不得像通关后的奖励商店」**：区块里没有「解锁 / 获得 / 奖励 / 新内容」任何字样；标题「带着记忆再来一遍」明确它是**重走**，不是**领取**。
4. **不泄露未解锁内容**：说明文案只说「你记得的会留下来」这种玩家已经拥有的东西（已解锁的结局、已读的日志、纪念品），不说具体增益（G1–G4 的具体内容在确认页才给，那是玩家主动点进去之后的权益）。
5. **不新增搜索类机制**——纯静态区块。

**区块文案（定稿候选，待用户拍板）**

| 位置 | 文案 | 备注 |
|---|---|---|
| 小标题 | `带着记忆再来一遍` | 与 `DIALOGUE.ngplus` 第 2 句「世界是新的——地面上的东西都回到原位，只有你带着记忆回来。」同调；也是确认页副标「带着记忆再来一遍」的同源措辞 |
| 说明行 | `地面上的东西会回到原位。你记得的会留下来。` | 一句话讲清「世界重置 / 记忆保留」，是 §1.4 确认页三段的**预告版**，不剧透具体清单 |
| 按钮 | `开始二周目`（`cycle >= 2` → `开始新的周目`） | **沿用现文案不动** |

> **边界自检**：说明行里没有「奖励 / 解锁 / 全部 / 新结局 / 额外」等词；没有「必须 / 应该 / 别错过 / 赶紧」等催促词。✔

#### B. 主菜单：给一个**次级文字入口**（推荐，解决 D1 / D5）

在 `StartScreen` 的按钮列**下方**（不是并列进按钮列，避免抬升权重）加一行文字链接，仅在 `ngPlusUnlocked(archive)` 为真时渲染：

```
[开始游戏 / 重新开始]
[继续游戏]
[图鉴]

  你已经走过 1 个结局，可以再走一遍 →     ← 次级文字链（新增）
```

- **为什么放主菜单**：这是玩家「错过结局页之后最可能回来的地方」，也是图鉴旁边最自然的位置（玩家刚看完「结局 1/5」，正是想看别的结局的时刻）。
- **为什么用文字链而不是按钮**：它不是主菜单的三个主动作之一（开始 / 继续 / 图鉴）。做成第四个按钮会让它看起来与「开始游戏」平级，反而制造「进游戏之前就要决定要不要二周目」的错觉——那正是「暗示必须」的失败形态。
- **文案定稿候选**：`你已经走过 {n} 个结局，可以再走一遍`（`n` 取 `archive.endings.length`）。**不用**「解锁」「奖励」等词。

> **⚠️ 实现风险（必须由工程处理，见 §5.3）**：主菜单状态下 store 里的 `save` 是 `createInitialState()` 的空档案（真实存档躺在 localStorage）。若直接调 `startNewCycle()`，会**用空档案覆盖当前存档**。工程必须走「先读档再开周目」的路径，不能照抄结局页的调用。

#### C. 改名区分「再来一次」与「开始二周目」（推荐，解决 D4）

| 现在 | 建议 | 理由 |
|---|---|---|
| `再来一次` | `重新开始这一遍` | 明确「重开**本周目**」，与「开新周目」区分开 |
| `开始二周目` | 不改 | 但**区块化后**（方案 A）它的上下文已经自解释 |

> 备选若用户觉得「重新开始这一遍」拗口：`重开这一遍`。**两者取其一即可，不要同时改两个按钮**（改名本身也会带来一次性的注意力转移）。

### 3.2 否决的方案（附理由）

| # | 方案 | 否决理由 |
|---|---|---|
| **X1** | 结局页给二周目加「奖励清单 / 解锁一览 / 你将获得」 | **直接违反边界 ①（不得看起来像通关后的奖励商店）**。二周目是「重来一遍」，不是领奖。现在的确认页有「本周目增益」一节已经踩在这条线上（但那是玩家主动点进来后的**权益说明**，位置合理，**不改**） |
| **X2** | 结局页把二周目入口升为 `btn--primary`，或挪到「留在这里继续」之上 | **违反边界 ②**：两个 primary 并列 / 或二周目排在留在这里之上，读起来就是「这才是正事，留在这里只是权宜」。会让玩家以为不走二周目就白玩，抬高门槛、破坏「可选自由模式」的定位。**保持非 primary 是刻意的** |
| **X3** | 主菜单放一个与「开始游戏」并列的大按钮 | 同上，且更糟：主菜单是「进入当前周目」的地方，一个平级按钮会让玩家每次开局都先做一次无关决策。改用 §3.1-B 的文字链 |
| **X4** | 常驻提示条 / 反复 toast 宣传二周目 | 噪音。更严重的是**反复宣传会把「可选」读成「应该」**，直接违反边界 ② |
| **X5** | 首次解锁时自动弹窗 / 打断式引导 | 打断结局的情绪落点。结局页的节奏是「盖章 + 结束语」，插一个营销弹窗会毁掉它。区块化（A）本身就是更好的「预告」——它出现在玩家需要它的那一屏，且不打断 |
| **X6** | 在图鉴里藏一个二周目入口按钮 | 图鉴是**看**的容器，开周目是**做**的动作，语境错位；且图鉴里点「开新周目」会丢当前进度，玩家误点成本高。若想在图鉴里提示，用 §3.1-B 的主菜单文字链即可，不必进图鉴 |
| **X7** | 改 `ngPlusUnlocked` 让一周目就可见 | **超出授权**（不改解锁条件），且实现注释已写明理由：「避免玩家在还没玩明白时把重开当成跳过」。**这是设计意图，不是缺陷（D6 不改）** |
| **X8** | 给二周目加「搜索 / 隐藏线索」类机制 | **违反边界 ④**，明确排除 |

### 3.3 可选（低优先，不在本次落地范围）

- **首次达成结局时给一句预告**：判定为**不需要**——方案 A 的区块本身就在玩家达成第一个结局的那一屏，是天然的、免费的、零噪音的预告。再加 toast 就是 X4。
- **「周目数」在主菜单可见**（如「第 1 周目」）：属于信息呈现的扩展，与本次「入口可发现性」不是同一问题，且会给玩家过早引入「周目」概念（D2 的解释负担）。**建议不做**。

## 4 · 玩家在什么时刻最可能想开二周目（设计依据）

| 时刻 | 玩家心理 | 现有承接 |
|---|---|---|
| **T1 · 达成第一个结局，站着看结局页** | 「结局还行，但好像没吃透」 | 入口就在这屏，但零解释、权重低（D2/D3） |
| **T2 · 点「回到开始页」之后** | 「这东西还能再来一遍吗？」 | **没有任何承接**（D1，最严重的缺口） |
| **T3 · 主菜单开图鉴看到「结局 1/5」** | 「还有别的结局」 | 图鉴可开，但没说「可以再走一遍」（D5） |
| **T4 · 二周目里退出、回主菜单** | 「继续」 | 无入口（但一次进入二周目后玩家已经知道它存在了，优先级最低） |

**方案 A 打 T1，方案 B 打 T2 / T3。** 两者合起来覆盖「第一次知道」和「错过之后回来」两类路径。

### 5.2 建议同批改（文案层面，解决 D4）

| 文件 | 改什么 |
|---|---|
| `apps/web/src/screens/EndingScreen.tsx` | 「再来一次」→ `重新开始这一遍`（或 `重开这一遍`，二选一）。同步更新该按钮上方的注释块（`:144-150`），说明改名原因（避免与「开新周目」混淆） |

### 5.3 ⚠️ 主菜单入口的实现约束（工程必须处理）

主菜单状态下，store 的 `save` 是 `createInitialState()` 的空档案（真实存档在 localStorage，见 `gameStore.ts:466-490`）。结局页的「开始二周目」能直接工作，是因为那时 `save` 就是真实存档；**主菜单没有这个前提**。

工程必须在下列三条里选一条，并**在 PR 描述里写明选了哪条**：

| 选项 | 做法 | 代价 |
|---|---|---|
| **E1（推荐）** | 主菜单点击时先 `continueGame()`（把 localStorage 存档读进 store，`gameStore.ts:569`），**成功后再** `openNgPlusConfirm()` | 会把玩家带进游戏画面（`screen: 'game'`），可能打断「我只是想看看说明」的意图 |
| E2 | 只在**有活动存档**（`hasSavedGame()` 为真）时渲染该入口，不显示任何说明 | 纯提示，不承诺任何动作；存档被清空时入口自动消失（可接受） |
| E3 | 新增独立 store action：读 localStorage 存档 → 用它构造新周目 → 跳过确认页直接开 | 绕过了确认页（玩家会看不到「保留/重置」清单）——**不建议**，确认页的存在价值就在于此 |

> **设计侧底线**：无论选哪条，**入口文案不得承诺任何尚未存在的东西**（不得出现「已解锁 X 个结局」以外的进度暗示）。

### 5.4 明确不改（防止实现越界）

- ❌ `packages/game-core/src/ngplus.ts` —— 不改 `ngPlusUnlocked`、不改 `startNextCycle`、不改 `NEXT_CYCLE_KEPT` / `NEXT_CYCLE_RESET`、不改 `DIALOGUE.ngplus`。
- ❌ 不改结局分支（`availableEndings` / `finishGame` / `chooseEnding`）。
- ❌ 不改 `NgPlusConfirm.tsx` 的三段内容与文案（保留/重置/本周目增益）——它是玩家**主动点进来之后**的权益说明，位置正确、文案已定稿。
- ❌ 不给二周目加任何「奖励 / 解锁 / 领取」字样；不把二周目做成 primary；不在主菜单放并列按钮；不新增搜索类机制。
- ❌ 不新增任何「已解锁内容预告」（不得泄露未解锁内容）。
- ❌ 不动 `docs/design/CONTENT-v3-NGPLUS-UI-COPY.md` 的 K1–K5 / R1–G4 文案——本次新增的三行文案（区块标题 / 说明行 / 主菜单入口）**若确认采用，需另起一笔补进 UI-COPY**（本轮未获授权改该文件）。

## 6 · 四条边界逐条自检

| 边界 | 本方案如何满足 |
|---|---|
| ① 不得让二周目看起来像「通关后的奖励商店」 | 区块标题「带着记忆再来一遍」、说明「地面上的东西会回到原位。你记得的会留下来。」——全篇零「奖励 / 解锁 / 获得 / 额外 / 新」字样；主菜单文案「你已经走过 1 个结局，可以再走一遍」是**陈述既有事实 + 描述动作**，不给奖励清单。**否决 X1** |
| ② 不得暗示「必须走二周目」 | 二周目**始终不是 primary**、不排在「留在这里继续」之上、不是主菜单的并列按钮（只是文字链）、说明文案不含任何催促词。**否决 X2 / X3 / X4** |
| ③ 不得泄露未解锁内容 | 说明文案只提「你记得的」（= 已解锁结局 / 已读日志 / 纪念品，都是玩家已有物）；不预告 G1–G4 的具体内容（那在确认页，玩家主动点进去才看）；不出现未解锁结局的名字；解锁判定本身不变（**否决 X7**） |
| ④ 不新增「搜索」类机制 | 全方案零新增机制、零新增状态字段、零新增存档写入；改动全部是展示层与一行文案（**否决 X8**） |
