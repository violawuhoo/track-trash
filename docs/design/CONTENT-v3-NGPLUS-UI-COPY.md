## 1 · 确认页 ·「保留」段（定稿 · 5 行）

| # | 显示文案（定稿） | 插入源 | 对应 core `fields` |
|---|---|---|---|
| K1 | 已解锁的结局（【N】个）—— 那几格不会灭 | `archive.endings.length` | `ngPlus.endings` |
| K2 | 读过的前任记录（【N】篇）—— 读过的不用再读一遍 | `archive.readLogs.length` | `ngPlus.readLogs` |
| K3 | 走过的支线（【N】条）—— 面板上会标出「上次走过」 | `archive.branchesHistory.length` | `ngPlus.branchesHistory` |
| K4 | 纪念品（【N】件）—— 你拿到的东西不会丢 | `archiveKeepsakes.length` | `keepsakes` |
| K5 | 这是你的第 【N】 周目 | `nextCycle`（= `archive.cycle + 1`） | `ngPlus.cycle` |

### 1.1 逐条说明

- **K1「那几格不会灭」**：图鉴里 5 格结局格子。不写「保留」这种界面词，写**玩家看得见的结果**——灭掉的格子重新亮起来是图形语言，「灭」直接接图鉴的视觉。
- **K2「读过的不用再读一遍」**：本页**最容易被误解的一条**（QA M-1）。玩家会以为「上周目读过的篇目二周目还得再合一次载体」——**不用**。`ngPlus.readLogs` 跨周目保留，已读篇目二周目打开即展开。
  - ⚠️ **K2 只承诺「读过的」，不承诺「没读过的」**。没读过的篇目在二周目要重新攒条件（载体重新合、`crafts` 重新计数）。这个区别由 R4 承担，两条合起来才是完整口径。
- **K3「面板上会标出『上次走过』」**：**直接引用 G3 的实际表现**，而不是说「走过的支线会被记住」。玩家在支线面板能看见那个「上次走过」标记——说「会被记住」是抽象，说「会标出来」可验证。带引号的「上次走过」必须与支线面板上的原文**一字不差**。
  - ⚠️ K3 **不许**暗示支线被解锁或已完成。支线在二周目**要重做**（`branches` 已重置，见 R3）。
- **K4「你拿到的东西不会丢」**：对应 GDD §7.5「纪念品全保留」。用「你拿到的东西」而不是「纪念品」——玩家未必记得哪些物件是纪念品，但记得「自己拿到过的东西」。
- **K5「这是你的第 N 周目」**：标题区已有「第 N 周目 · 带着记忆再来一遍」，保留段再出现一次是**有意的**：保留/重置两段讲的是「什么留、什么走」，周目数属于「留下」的一侧（`cycle` 确实跨周目累加）。

### 1.2 排版建议（不改文案，只改渲染）

- 「——」后的后果说明用次要色（灰），让**字段名**（前半段）是视觉主体。
- 计数**不加分隔符**（不加「共」字、不加千分位）。
- 变量替换后若 `N = 0`，整行**照常显示**（例：`走过的支线（0 条）—— 面板上会标出「上次走过」`）。**不隐藏空行**——隐藏会让玩家以为这条不存在，反而是信息缺失。

| R3 | 已完成的支线 —— 但还是得重新做一遍 | `branches` |

> 若工程希望压到 5 行（与现有 UI 行数一致），**唯一允许的合并**：

> **R4 / R5 不得合并进任何别的行，也不得彼此合并** —— 它们的后果是本页唯一不可省的两条（见 §2.2）。

### 2.1 逐条说明

- **R1「回到坠毁点的第 1 天」**：`day`(=1) + `areaId`(=crash) 的合后果。写「第 1 天」而不写「天数归零」——玩家的时间感是「天数」。
- **R2「建设期得重新走满」**：这一句单独点名 `buildDone`，是因为 `buildDone` 决定**《数据卷盘》（L8）还读不读得了**（`logs.ts` 里 L8 的解锁条件是 `unlock: { buildDone: true }`，`logUnlocked()` 判 `if (u.buildDone && !state.buildDone) return false`）。`buildDone` 归零后 L8 **重新上锁**，玩家在二周目读不到这一篇 —— 不点名，玩家会在二周目发现它不见了，以为是 bug。
  - ⚠️ **订正（2026-10-22 · 文策渊）**：本条原先写作「`buildDone` 决定**第四支线（留下来）是否可见**（GDD §2.4）」，**与实现不符** —— GDD §3.6 设计的第四支线可见性门控（`requiresBuild` 字段）**在实现中尚未落地**（支线面板无条件列出全部四条），所以 `buildDone` 归零**不会**让第四支线消失。这是**实现层滞后**，不是本条文案的错误；**R2 的玩家可见文案本身不动**（它对 `buildDone` 的描述「回到第一个阶段的第 1 步，建设期得重新走满」依然成立且正确）。
  - 顺带说明：GDD §7.1 重置表里 `buildDone` 一行的「对玩家的后果」已同步订正为「**L8《数据卷盘》重新上锁**」，并注明第四支线可见性门控未落地。
- **R3「但还是得重新做一遍」**：用「重新做一遍」不用「清空」——「清空」听起来像永久失去，「再做一遍」才是实话（`branchesHistory` 还留着，走过的支线仍会在面板上标「上次走过」，见 K3）。
- **R4「上周目没读完的那几篇记录，要重新攒次数才能读」**：**本页最重要的一条**。QA 把它定为 major 的理由就是玩家会低估二周目的收集难度。
  - 「攒次数」= 累计合成次数 `crafts`。玩家能理解「合成得够多才解锁」这件事（解锁条件写在日志面板上）。
  - 「上周目**没读完的**那几篇」这个限定词是**必须的**：它同时暗示「读过的那些不用重读」，与 K2 呼应。**不许写成「所有记录都要重新攒次数」**——那是错的（`readLogs` 跨周目保留）。
  - 不写具体数字（3 次 / 14 次）：解锁条件在日志面板里写明，确认页不必复述，避免给一个记不住的数当成承诺。
- **R5「载体是要用掉的，不带过去」**：`logsFound` 清零。`logsFound` 是「本周目合出过哪些载体」的记账，而载体本身是可消耗物品——「用掉的」三个字把两层意思一次说清：载体消耗不撤销记录（所以「拿到过」这层信息也一并没了）。
- **R6**：保持现有文案。这两项玩家没有情感投入，不加后果说明。
- **R7「结局本身已经记在『已解锁的结局』里了」**：把「结局被清掉」和「结局不会丢」两件事一起说清——玩家看到 R7 会以为二周目里那 5 格图鉴会清空，这一句正好堵住这个误会。
- **R8**：纯计数器，**不加后果说明**（玩家不会因为它归零而困惑）。

### 2.2 R4 / R5 为何不可合并

这两条是 QA M-1 的全部内容。它们**指向两件不同的事**：

- R4 指向**「读日志的门槛」**（解锁条件里的合成计数）；
- R5 指向**「本周目拿到过什么」**（图鉴里的载体三态）。

合并成一句「累计合成次数和这一周拿到的记录载体」，玩家读完只知道「有两样东西没了」，**不知道它们各自会让自己多做什么**——这正是 QA 判 major 的原因（「玩家会低估二周目的收集难度」）。

### 2.3 R4 的口径边界（防止过度承诺）

R4 只说「要重新攒次数才能读」，**不说**「哪些记录要重新攒」。理由：具体是 L1（3 次）与 L5（14 次），写在日志面板的解锁条件里。确认页给**机制**不给**清单**——清单会随版本变，机制不会。

## 4 · G2 阶段 1 目标提示 · 三步示例文案（定稿）

**落点**：`packages/game-core/src/ngplus_gain.ts` 的 `pairingExample()` 生成的 `text` 字段（挂在阶段 1 三步的目标提示里）。

### 4.1 句式模板（定稿）

```
这一步要「【标签A】」和「【标签B】」——比如【物品A名】（【标签A】）配【物品B名】（【标签B】）。带这两个标签的都行，不一定是这两样。
```

- **标签在前，例子在后**（QA m-3 的建议）：先说「要什么」，再说「大概长什么样」。这样玩家的心智模型是「我需要两个标签」，不是「我需要某个具体物件」。
- **尾巴固定为「带这两个标签的都行，不一定是这两样。」**
  - QA m-3 建议的旧写法是「同一类里换别的也行」——**本轮不用**。理由：「同一类」里的「类」指什么（物品类别？标签？）玩家要自己猜；新写法直接点名「标签」，把可替换的条件说清楚。
  - 这一句是**硬保底的人工对应物**：真正保证可达性的是 `distribute()` 的标签硬保底（当前步骤缺的标签必定刷出带该标签的物品）+ 判定是标签并集覆盖。文案说「带这两个标签的都行」，正好对应这两条机制。
- **禁止出现的措辞**：「照着做一定能过」「照这个拿准能过」「唯一配方」「正确配方」。示例是方向提示，不是步骤，也不是唯一解。

### 4.3 示例物品取值的定稿（含对工程的一处改动请求）

**`STAGE1_EXAMPLES` 定稿为：**

```ts
's1-1': ['battery', 'tape'],
's1-2': ['wrench', 'crowbar'],   // ← 相对工程现状改为 wrench（原为 battery）
's1-3': ['manual', 'battery'],
```

**为什么 s1-2 从 `battery` 换成 `wrench`（QA m-3）**：

1. **工程现状是三步全部点名 `battery`**（s1-1 / s1-2 / s1-3）。玩家做完 s1-1 之后 `battery` 已被 `craft()` 扣掉，s1-2 / s1-3 的提示却还在说它 —— 这不是软锁（标签硬保底保证「导电」必定可得），但**观感上是「教程在指一本你刚花掉的书」**。
2. 坠毁点池里带「导电」的 base 只有两件：`battery`、`wrench`；三步各自需要一个「导电」，所以**至少一件导电物品必然在两步里重复**——这是池子只有 9 件 base 的硬约束，**换不出「三步零重复」的组合**。
3. 因此正确的解法不是追求零重复，而是：**把重复降到最少 + 把「重复的那件」放在跨度最大的位置 + 用文案把「标签才是硬要求」顶到最前**。
4. 定稿方案的分布是：`battery` 出现在 s1-1 与 s1-3（**首尾两步，跨度最大**），`wrench` 单独出现在 s1-2。玩家在 s1-1 用掉 `battery` 之后，s1-2 的提示指向的是**另一件他还没用过的**东西；到了 s1-3 才再次点到 `battery` —— 但那时他已经见过两件不同的导电物品，**心智模型已经是「要带导电标签的东西」而不是「要漏气电池」**。这正是 §4.1 模板句式要达到的效果。

**⚠️ 附带的两处工程改动请求（都属于文案层，不改判定）**：

| # | 请求 | 位置 | 理由 |
|---|---|---|---|
| C-1 | `STAGE1_EXAMPLES['s1-2']` 由 `['battery','crowbar']` 改为 `['wrench','crowbar']` | `ngplus_gain.ts` | §4.3 第 4 点。`wrench` 是 base 且在坠毁点池内，`stage1ExampleItemsInCrash()` 断言仍然通过；`wrench` 带「导电+金属」，标签归属由 `requires.find(...)` 取首个命中 → 显示为「导电」，`crowbar` 带「金属」→ 覆盖 `{导电, 金属}` ✅，两件各贡献一个必需标签 ✅，无凑数材料 ✅ |

### 4.4 标签中文名写法（定稿）

- **直接用 `requires` 里的标签原样，不做改写、不加书名号、不加解释**：`导电` / `金属` / `粘` / `知识`。
- 四个标签名的玩家可读性已核过：`粘` 单独出现略短，但它是游戏内既有标签名（物品标签栏、`BRANCH.requires` 都在用），**换成「黏」或「粘性」会造成两套叫法**——保持一致优先。
- 标签出现在提示里时**一律用「」包住**，与游戏内其他提示的引号用法一致。

### 4.5 s1-1 的 `tape` 与 `ducttape` 说明（预防工程侧疑问）

s1-1 的 requires 是 `['导电', '粘']`，坠毁点带「粘」的 base 有两件：`tape`（胶带）、`ducttape`（银色管道胶带）。定稿选 `tape`，因为「胶带」是更常见的词；`ducttape` 的名字自带「银色管道胶带」七字，出现在一行提示里太重。**两件都合法**，选 `tape` 仅为可读性。

### 4.6 m-3 的结论（是否构成软锁）

**不构成软锁。** 三条依据：

1. `distribute()` 对「当前步骤缺的标签」做**硬保底**（`packages/game-core/src/world.ts` 的 `missingForBag`）—— 当前步骤要「导电」「金属」时，地面必定刷出带这些标签的物品。
2. 判定是**标签并集覆盖**（`resolve.ts`）—— 捡到哪一件带该标签的物品都能过，不依赖具体物件。
3. 每个标签在坠毁点池里都有 ≥2 个 base 来源（导电 `battery`/`wrench`、金属 `wrench`/`crowbar`、粘 `tape`/`ducttape`、知识 `manual`/`photo`），**同一类里换别的也行**这句话有事实支撑。

**真正的风险不是软锁，是「误导」**（玩家以为三步都要同一件 `battery`）。§4.1 的句式 + §4.3 的取值分布 + §4.4 的一致标签名，三者共同消解。

### 6.2 逐条说明

- **T1「带着记忆再来一遍」**：与 `DIALOGUE.ngplus` 第 2 句（「世界是新的——地面上的东西都回到原位，只有你带着记忆回来。」）同调，也是确认页副标「第 N 周目 · 带着记忆再来一遍」的同源措辞。**不用「二周目」「重开」「再来一局」**——前两个是内部术语 / 歧义词，后者把这一遍说成「重置」。
- **T2「地面上的东西会回到原位。你记得的会留下来。」**：一句话讲清「世界重置 / 记忆保留」，是确认页三段（保留 / 重置 / 本周目增益）的**预告版**，不剧透具体清单。
  - 只承诺玩家**已经拥有**的东西（已解锁结局 / 已读日志 / 纪念品），**不预告未解锁内容**，也不点名 G1–G4 的具体增益（那是确认页的权益说明，玩家主动点进去才看）。
  - **不含**「奖励 / 解锁 / 获得 / 额外 / 新」等字样，也**不含**任何催促语气（「应该 / 别错过 / 赶紧」）——它描述「会发生什么」，不是「你应该去」。
- **T3「再走一遍」**：短、指向明确，且与 T1「带着记忆再来一遍」**不重复**（一个说「带着什么」，一个说「做什么」）。
  - ⚠️ **原「开始二周目」/「开始新的周目」一律作废**。理由：区块标题已经解释了「再来一遍」，按钮若还叫「开始二周目」会与之重复，且把玩家不认识的词推到最前面。
  - ⚠️ **不区分周目序号**：T3 是固定文案，`archive.cycle >= 2` 时**也**写「再走一遍」——原来那个 `cycle >= 2 ? '开始新的周目' : '开始二周目'` 的分支**一并删掉**（T3 是固定字符串，无变量）。
- **T4「重新开始这一遍」**：与 T3 明确区分开——T4 是**重开本周目**（世界清零、不带新记忆），T3 是**带着记忆再走一遍**。
  - ⚠️ **不用「重开这一遍」**：「重开」在中文里更像「重开一局」，暗示把之前那遍作废；「重新开始这一遍」明确指向「同一段的另一次」，与二周目的语义一致。
  - ⚠️ **T3 与 T4 必须同批改**：只改一个，两个按钮仍会互相混淆。
- **T5「你已经走过 N 个结局，可以再走一遍 →」**：主菜单的次级文字入口（**不是按钮**，不与「开始游戏 / 继续游戏 / 图鉴」平级）。
  - 「N 个结局」是玩家能理解的进度感，不是炫耀；「可以」表明**可选**；「→」给出可点性提示但保持次级视觉。
  - 仅在 `ngPlusUnlocked(archive)` 为真时渲染（**不改这个判定**）。
